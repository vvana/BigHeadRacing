# Аналитика: сбор метрик и веб-панель

**Панель: https://daf.autovsauto.ru/?k=ПАРОЛЬ** (пароль — в
`/opt/bhr-metrics/config.json` на VDS, печатается и в журнале службы при
первом запуске). Ссылка с `?k=` кладёт пароль в cookie на год — дальше
достаточно открыть `https://daf.autovsauto.ru/`.

Сертификат Let’s Encrypt Caddy выпускает и продлевает сам. Сама служба
слушает только `127.0.0.1:8090` — снаружи она доступна ТОЛЬКО через Caddy,
прямой порт закрыт (10.09).

## Как устроено

```
игра (клиент)              ворота (VDS, процесс игры)        панель (VDS)
Analytics.gd  ──ENet 9990──▶ SocialServer._metric  ──файл──▶ bhr-metrics
  очередь событий            user://metrics/<дата>.jsonl      SQLite + 127.0.0.1:8090
```

1. **`scripts/Analytics.gd`** (автозагрузка в игре) складывает события в
   очередь `user://metrics_queue.json` и отправляет их серверу друзей по
   уже работающему соединению (UDP 9990, сообщение `{t = "metric", e, d}`).
   Очередь нужна затем, что игрок часто играет без связи: оффлайн-заезды
   уезжают в аналитику при следующем выходе на связь, а не теряются.
   Ни отдельного порта, ни TLS, ни разрешения «cleartext» на Android для
   этого не нужно — это главная причина, почему метрики идут через ENet, а
   не своим HTTP-запросом.
2. **`scripts/SocialServer.gd`** принимает событие, проверяет имя события
   (белый список `METRIC_EVENTS`), длину строки (`METRIC_MAX_LEN`) и
   частоту (`METRIC_PER_MIN` на соединение) и дописывает строку JSON в
   `user://metrics/<ГГГГ-ММ-ДД>.jsonl`. Плюс сервер САМ пишет событие
   `hello` при каждом входе игрока — «сколько игроков заходит» считается
   даже для старых сборок без `Analytics`.
3. **`server/metrics/server.js`** (эта папка) раз в 20 секунд дочитывает
   новые строки этих файлов (помнит смещение по каждому файлу), кладёт их
   в SQLite и показывает панель (её проксирует Caddy с TLS).

Событий в игре семь: `session` (запуск), `race` (финиш заезда), `soccer`
(матч), `ad` (досмотренный ролик), `buy` (покупка), `level` (взят уровень),
`party` (заезд командой) — плюс серверный `hello`. Что внутри каждого —
см. шапку `scripts/Analytics.gd`.

Личного в метриках нет ничего сверх того, что сервер и так знает: uid
профиля и имя (они в реестре имён), платформа, версия сборки. Ни адресов,
ни переписки, ни содержимого профиля.

## Что показывает панель

- **Сводка**: игроков всего, новых за 7 дней, играли сегодня и за неделю,
  заездов, матчей, роликов рекламы, покупок, удержание D1/D7.
- **Графики по дням** (30 суток): игроки и новички; заезды, матчи, входы;
  ролики рекламы; потраченные монеты.
- **Машины**: заезды по каждой машине (что любят), доля, среднее место,
  победы, число игроков; отдельно — покупки машин.
- **Заезды**: по сети против одиночных, в команде, средняя длительность,
  среднее место, трассы, размер заезда, **какое оружие применяют**.
- **Деньги и реклама**: ролики, пары (награда +500), выданные монеты,
  сколько игроков вообще смотрят рекламу, покупки по типам, что покупают
  чаще, взятые уровни.
- **Платформы и версии сборки**, воронка «зашёл → заезд → пять заездов →
  покупка».
- **Таблица игроков** и лента последних событий.
- **Выгрузка `/api/export.csv`** — все события одним файлом для Excel или
  Python (разделитель `;`, UTF-8 с BOM).

## Обслуживание

```bash
systemctl status bhr-metrics
journalctl -u bhr-metrics -f
cat /opt/bhr-metrics/config.json        # пароль панели и настройки
ls -la "/home/bighead/.local/share/godot/app_userdata/Пыль и Пламя/metrics"
```

Обновить панель с рабочей машины — `Обновить аналитику.bat` в корне
проекта (заливает `server.js` и юнит, перезапускает службу). Игровую часть
метрик (`Analytics.gd`, `SocialServer.gd`) везёт обычный
`Обновить сервер.bat`.

Настройки — `/opt/bhr-metrics/config.json` (создаётся при первом запуске):

| Поле | Смысл |
|---|---|
| `port`, `host` | где слушает панель (сейчас `127.0.0.1:8090`, наружу — через Caddy) |
| `metricsDir` | папка с `<дата>.jsonl` игрового сервера |
| `dbPath` | файл SQLite (`data/metrics.db`) |
| `tzOffsetHours` | часовой пояс для границ суток в отчётах (3 — Москва) |
| `token` | пароль панели |

Зависимостей нет: только встроенные модули Node (`node:sqlite` есть с
Node 22). Расход — около 40–60 МБ RAM, поэтому служба спокойно живёт рядом
с игровым сервером на VDS 960 МБ.

## Чего пока нет (осознанно)

- **Заезды, которые сервер судил сам.** Метрику `race` шлёт клиент. Если
  игрок вышел, не дождавшись финиша, заезда в статистике не будет.
- **Web-сборка (Яндекс Игры).** Там UDP нет вовсе, метрики собирает
  платформа; `Analytics` в web-сборке выключается сам.

## Если захочется готовый сервис вместо своего

Своя панель выбрана потому, что этот VDS — 1 ядро и 960 МБ: PostHog,
Countly и Matomo требуют кратно больше. Разумные готовые варианты, если
игроков станет много:

| Сервис | Чем хорош | Чем неудобен |
|---|---|---|
| **Яндекс AppMetrica** | бесплатно и без лимита событий, живёт в России, есть воронки, когорты, удержание, push | нужен нативный плагин для Godot на Android; веб-сборка отдельно |
| **Firebase / Google Analytics for Games** | бесплатно, стандарт индустрии, готовые отчёты по удержанию и монетизации | плагин для Godot, аккаунт Google, данные вне России |
| **GameAnalytics** | сделан именно под игры: прогрессия по уровням, экономика (источники и стоки монет), реклама | лимиты бесплатного тарифа, свой формат событий |
| **PostHog Cloud** | продуктовая аналитика с воронками и сессиями, щедрый бесплатный тариф | не игровой профиль, нужен HTTP-клиент из игры |
| **Umami / Plausible (self-hosted)** | лёгкие, свои данные | это веб-аналитика: события игры в них укладываются криво |

Наш сбор им не мешает: события уже уходят одной точкой
(`Analytics.push_event`) — добавить второго получателя можно, не трогая
остальную игру.
